ForgeGraph

Evidence-Grounded AI for Air-Gapped Predictive Maintenance

ForgeGraph evolves the 1500-ton forging-press predictive-maintenance lab from direct prompt-based diagnosis into a retrieval-augmented workflow that shows the maintenance evidence behind each advisory recommendation.

Source repositorySession 1 codelabSession 2 codelab

1. Motivation

The original codelab stores simulated sensor readings in AlloyDB Omni and asks a local Gemma model to analyze potentially anomalous readings. That is a useful starting point, but an engineer also needs to know which maintenance procedure or historical incident supports an AI-generated hypothesis.

2. What ForgeGraph adds

Hybrid signals

Transparent thresholds for hydraulic pressure, oil temperature and vibration identify a candidate anomaly before an LLM is called.

Semantic evidence retrieval

EmbeddingGemma embeds maintenance-document chunks; AlloyDB Omni stores vectors and retrieves relevant chunks using cosine distance; a curated relationship graph connects symptoms to possible components, synthetic incidents and inspection procedures.

Grounded local analysis

Gemma receives the measured readings and retrieved excerpts. The prompt asks it to distinguish facts from hypotheses and cite evidence IDs.

Failure-aware UI

The UI labels rule-based demo results distinctly, shows missing-model errors, safely renders output as text and keeps sensor visualization independent.

In the no-cloud demo mode, retrieval uses transparent lexical overlap and the fallback analysis is rule-based. It is explicitly labelled as a demo rather than being presented as real Gemma output. The AlloyDB mode requires model registration and private endpoints from the official deployment codelab.

5. Run locally

python -m venv .venv
source .venv/bin/activate  # Windows: .venv\\Scripts\\activate
pip install -r requirements.txt
cp .env.example .env
python app.py

Open http://127.0.0.1:5000. The default demo does not need Cloud credits. To enable real model responses, configure an appropriate reachable OpenAI-compatible Gemma endpoint in GEMMA_API_URL. To enable semantic vector retrieval, configure APP_MODE=alloydb, DATABASE_URL, register the EmbeddingGemma model as described by Session 2, and run python scripts/seed_database.py.

6. Verify and test

pytest -q
python scripts/check_config.py

The tests cover threshold classification, invalid sensor values, retrieval ranking, response parsing for Ollama/OpenAI-shaped payloads, evidence-aware prompt construction, and demo-mode labelling. The CI workflow runs the same suite on pushes and pull requests.

7. Deploy to Kubernetes

The provided k8s/forgegraph-app.yaml is a starting manifest for the web service. Build and push the image to your registry, update the image path, create a Kubernetes secret called forgegraph-secrets with key database-url, and update the Gemma service DNS to match your serving deployment. Follow the official codelab for AlloyDB Omni, EmbeddingGemma/TEI and Gemma serving setup.

docker build -t YOUR_REGISTRY/forgegraph:latest .
docker push YOUR_REGISTRY/forgegraph:latest
kubectl apply -f k8s/forgegraph-app.yaml

Cloud deployment can incur charges. Use the codelab's cleanup instructions and verify that the cluster, VM, load balancers and other billable resources are deleted when finished.

8. How this evolves the original codelabs

Session 1 demonstrates anomaly detection with direct Gemma analysis. Session 2 demonstrates AlloyDB Omni on GKE, EmbeddingGemma, model registration and vector similarity search. ForgeGraph combines these foundations into an evidence-grounded industrial workflow with document ingestion, citations, failure-state handling, automated tests and an app deployment manifest.
